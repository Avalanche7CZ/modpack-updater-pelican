# Logical mod JAR upgrades

A mod version replacement is one `kind=mod_upgrade` plan row. It contains the authenticated baseline JAR, the installed JAR, the target JAR, their hashes, embedded versions, complete ID set, member paths and conditional mutations. File Changes and Mods & Files each show that row once. Searching matches installed, baseline and target filenames as well as the embedded identity.

Identity is established by Forge `META-INF/mods.toml` or NeoForge `META-INF/neoforge.mods.toml` parsed from the exact checksum-bound JAR bytes. Bundled mods use a complete ID set and preserve per-ID versions. A duplicate ID, overlapping/changed bundle, conflicting administrator alias, unreadable mod scope or unavailable identity requires review. A verified Forge library/language-provider manifest is distinguished from an unidentified active mod; no filename heuristic is used.

An unchanged installed JAR produces `upgrade_mod`, with explicit conditional remove/install members under that one logical operation. A locally changed JAR produces `mod_upgrade_conflict`. Keep local protects the whole operation and suppresses the target addition. Use upstream applies a deliberate policy to the whole known path set, including bundled-ID JARs and existing exact member rules. Unverified or duplicate identity problems cannot be authorized away with a replacement policy; refresh evidence and resolve the ambiguity first. Existing protections preserve the whole mod automatically. Local-only mods are preserved, and a newly introduced upstream filename cannot silently add a second copy of an installed mod. Intentionally absent or disabled mods remain absent/disabled.

The filesystem worker now returns metadata bound to the JAR's SHA-256, source descriptor and all embedded versions. Older snapshots may refresh only changed JAR metadata from retained verified stages through the read-only `stage_mod_metadata` operation; the complete serverpack need not be downloaded again. Identical live bytes may establish baseline metadata. Missing retained source evidence remains a blocker. Remote workers need this update too. Baseline and target remain exact release identities, so comparing across multiple releases needs no intermediate installations.

The prepared offline transaction first rechecks the complete approved active-JAR set. It records recovery intent and both member paths, copies and fsyncs a verified candidate, retains the old JAR under a hidden non-JAR name, then publishes the target without overwriting an unexpected destination. Old and new active filenames are never deliberately installed together. Failure attempts to return the original and otherwise requires the existing locked full-backup restore and stopped recovery checkpoint. This is a logical offline transaction, not a claim that POSIX supports one atomic rename of two different filenames. Existing full backup, exact approval, world protection and full-restore verification remain required.

**Production deployment of this new operation remains blocked.** `PreviewService` and `DeploymentGate` reject deployment plans containing `upgrade_mod`; an environment flag cannot qualify it. Automatic deployment stays disabled. The real TFG 0.13.15 → 0.13.17 [source fixtures](../tests/fixtures/tfg-0.13.15-to-0.13.17/README.md) are collected, but no planner, browser, transaction or CI tests were run for this change, as requested. Browser actions retain the previously implemented loading, renderless persistence, durable comparison receipt and sanitized error feedback; their logical-mod behavior still needs browser qualification before production apply can be enabled.
