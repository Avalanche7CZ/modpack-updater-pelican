# Mod upgrades

Verified upstream manifests establish file ownership by path and hash. An ordinary upgrade can remove the old manifest-owned JAR and install the new one without requiring embedded metadata from every installed mod. Unchanged pack files and unrelated custom JARs are not scanned.

When upstream metadata identifies the same mod in both releases, File Changes groups the old and new JAR into one mod upgrade. The installed old JAR is checked against its original hash. A local modification becomes a conflict; Keep local preserves the known operation, while Use upstream explicitly permits replacement. Protection of either member preserves the whole known operation. Known absent/disabled mods remain absent. Duplicate or overlapping identities within the candidate operation require review; an unrelated JAR with missing metadata does not block it.

Native Compare checks for alternate installed Forge/NeoForge JARs when an upstream mod changes and its expected installed path is missing. It lists only `mods/` and uses upstream filename stems or an explicit local mapping to select candidates. A legacy authenticated baseline with an ID and loader but no metadata source can guide this search when the new release has verified embedded identity for the same mod and loader. Live JARs still require byte and embedded ID verification before they enter the plan. A single active alternate appears as a locally modified mod. If approved, the exact old path is retired and the verified target is installed in the same backed-up transaction. A disabled JAR stays disabled. Unreadable or ambiguous candidates are not silently installed. This does not detect arbitrary renamed JARs without a mapping or validate the complete Forge dependency graph. After upgrading the plugin, run Compare again before approving a native update.

If no identity is available, the planner uses ordinary conditional file operations from the manifest delta. A missing old JAR causes possible replacement additions to require review rather than silently re-enabling a locally removed mod. This does not prove that independently added custom JARs have no duplicate mod IDs: the updater intentionally does not parse the entire live mod directory. Dependencies and actual Minecraft startup remain subject to the normal startup check and native rollback.

A grouped upgrade copies and verifies the target beside its destination, hides the old JAR, publishes the new one and records recovery information. Ordinary file operations likewise check current and installed hashes. All mutations run offline, after a completed locked Pelican backup. Failed apply/start requests the exact native restore and checks the original startup. There is no blanket “logical mod deployment disabled” gate.

The TFG release fixtures cover nine grouped upgrades, bundled IDs, custom-file protection, modified/absent/disabled JARs and missing optional metadata. Native Pelican integration covers actual queued manual and automatic mod deployment, backup callbacks and restore failure scenarios. Live production TFG updates still need operational verification on the user's server.
